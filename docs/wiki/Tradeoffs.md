### T1. 학습, MLflow, 서빙을 컨테이너 한 대에

| 상황 | 재학습한 모델을 서빙이 바로 읽어야 하는데, 팀원 PC 마다 환경이 다르다 |
|---|---|
| 선택지 | (a) MLflow 트래킹 서버, 서빙 컨테이너 분리 (b) 한 컨테이너 안에서 sqlite MLflow |
| 결정 | (b). 학습과 서빙이 같은 파일시스템(`/app`) 을 보므로 아티팩트를 네트워크로 찾아갈 일이 없다 |
| 비용 | 컨테이너를 다시 만들면 재학습 이력이 사라진다. 인스턴스를 여러 대 띄울 수 없다 (캐시 동기화도 없음) |
| 다시 볼 조건 | 서빙 인스턴스가 2대 이상이 되거나, 재학습 이력을 보존해야 할 때. 그때는 T7 의 `stale` 이 실제 경보 역할을 한다 |

### T2. 이미지 빌드 시점에 학습까지 끝낸다

| 상황 | 빈 컨테이너로 시작하면 업로드, baseline, MLflow 학습을 순서대로 해야 예측이 된다 |
|---|---|
| 선택지 | (a) 기동 후 초기화 스크립트 (b) `Dockerfile` 에서 시드 업로드 → baseline → 등록 |
| 결정 | (b). `up --build` 한 번이면 v1 이 Production 인 상태로 뜬다 |
| 비용 | 이미지 3.26GB, `--no-cache` 빌드에 학습 32.6초 포함. 데이터가 바뀌면 이미지를 다시 굽는다 |
| 다시 볼 조건 | 학습 데이터가 자주 바뀌거나 학습 시간이 길어질 때 |

### T3. 재학습은 warm start 3 epoch

| 상황 | 드리프트가 나면 최근 21일(+선행 20일) 로 다시 맞춰야 한다 |
|---|---|
| 선택지 | (a) 처음부터 재학습 (b) Production 가중치에서 10 epoch (골격 기본값) (c) 3 epoch |
| 결정 | (c). 21일로 scratch 학습은 불안정하고, epoch 를 늘릴수록 최근 3주에 과적합했다. 3/10/30 epoch 의 게이트 실패가 3/8/16회 |
| 비용 | 한 번에 치우침을 절반쯤만 줄인다. 수준 이동 시연에서 승격이 두 번 필요했다 (bias +1,958 → +1,220 → +475) |
| 다시 볼 조건 | 검증 구간을 5일보다 길게 잡을 수 있을 때 |

### T4. 드리프트는 bias 로 판정, RMSE 는 구조 알림

| 상황 | 골격은 "21일 RMSE > 임계값이면 재학습" |
|---|---|
| 선택지 | (a) RMSE 단독 (b) \|bias\| 단독 (c) bias 로 재학습, RMSE 는 알림 |
| 결정 | (c). 보간 모델도 21일 RMSE > 2,700 인 날이 107일, RMSE 트리거 10회 중 7회는 bias ±800 안쪽. 재학습 3배에 RMSE 개선 0 (3,039 vs 3,038) |
| 비용 | 주간 진폭만 커진 변화(ac(7) 0.17 → 0.67) 는 자동으로 못 고친다. 41행 fine-tuning 으로도 안 줄었다 (3,142 → 3,238) |
| 다시 볼 조건 | 피처나 모델 구조를 바꿀 수 있을 때 |

임계값 500 의 근거: 보간 데이터에서 21일 bias 는 ±1,000 안에서 움직여 1,500 이면 2025년에 3월 한 번, 2,000 이상이면 0회 걸린다. 500 이면 2025년 재학습 10회, 승격 9회, 롤백 1회.

### T5. 결항일은 학습에서 보간, 서빙에서는 이상치로 분리

| 상황 | 폭설 결항일(최저 1,042명) 이 스케일러를 누르고 MSE 를 지배했다 |
|---|---|
| 선택지 | 데이터 변형 A~G (기간 축소, 로그 변환 등), 결항일 보간 |
| 결정 | 학습 데이터에서 도착 25,000명 미만 18일을 양옆 평균으로 보간. 서빙 배치는 raw 그대로, 하루 오차 10,000 초과는 이상치 |
| 비용 | 학습 데이터가 실제와 다르다. 3월 18일 학습 컷의 마지막 값은 3월 19일 원자료로 보간돼 미래 정보가 섞였다 (재확인 필요로 기록) |
| 다시 볼 조건 | 결항 자체를 예측해야 하는 요구가 생길 때 |

결과: 평상시 RMSE 2,415 → 1,807, 예측 표준편차 445 → 1,898 (실제 2,444).

### T6. 롤백은 "미확정 승격" 에만

| 상황 | 재학습 모델이 1분기 저점에 과적응해 다음 윈도우에서 v1 보다 나빴다 (3,918 vs 3,126) |
|---|---|
| 선택지 | (a) 롤백 없음 (b) 반대 부호 bias 면 롤백 (c) 승격 뒤 첫 드리프트의 재학습이 게이트 실패면 롤백 |
| 결정 | (c). 조건 설명이 가장 단순하다. 승격 뒤 정상 윈도우가 한 번 나오면 확정 |
| 비용 | 승격 기록(`_last_promotion`) 이 메모리에만 있어 재시작하면 롤백 대상을 모른다. 롤백 시연의 게이트 실패 2,742 vs 2,700 은 간발이라 PC 에 따라 뒤집힐 수 있다 |
| 다시 볼 조건 | 서버 재시작이 잦아지면 MLflow 태그로 옮긴다 |

### T7. `stale` 은 run_id 우선, 모르면 null (C 담당)

| 상황 | 레지스트리는 v2 인데 서버는 v1 을 들고 응답할 수 있다. 예측값만으로는 구분이 안 된다 (v1, v2 모두 39,980.96) |
|---|---|
| 선택지 | (a) 등록 번호 비교 (b) run_id 비교 (c) run_id 우선, 없으면 번호, 같아 보여도 근거 없으면 null |
| 결정 | (c). run_id 는 같은 번호의 재등록까지 잡는다. 번호가 같다고 false 를 주면 "확인했고 문제 없다" 는 근거 없는 안심이 된다 ([#22](https://github.com/wonn2k/skala-model-serving/pull/22)) |
| 비용 | 클라이언트가 true / false / null 세 상태를 다뤄야 한다 (대시보드는 null 을 "일치 미확인" 으로 표시) |
| 다시 볼 조건 | stage 대신 alias 로 옮길 때 판정 키를 다시 정한다 |

### T8. 버전 조회는 타임아웃 5초, 재시도 없음 (C 담당)

| 상황 | 트래킹 서버가 무응답이면 MLflow 기본값으로 848.03초를 막았다. sync 핸들러라 스레드풀 슬롯을 하나 문다 |
|---|---|
| 선택지 | (a) 기본값 (b) 재시도 1회 (10.68초) (c) 5초, 재시도 없음 (5.70초) |
| 결정 | (c). 조회 전용이라 재시도 가치가 낮다. `setdefault` 라 운영 환경변수가 이긴다 |
| 비용 | 일시적인 네트워크 흔들림에도 바로 `registry_error` 가 보인다 |
| 다시 볼 조건 | 버전 조회 결과가 자동 동작의 선행 조건이 될 때 |

### T9. 조회 실패를 숨기지 않는다 (C 담당)

| 상황 | "모델 없음", "URI 오타", "서버 다운", "mlflow 미설치" 가 모두 `production: null` 로 보였다 |
|---|---|
| 선택지 | (a) null 하나로 뭉갬 (b) 예외 메시지를 `registry_error` 로 (c) (b) + 본 저장소 `tracking_uri` 노출 |
| 결정 | (c). sqlite 오타는 MLflow 가 빈 DB 를 만들어 예외 없이 0건을 돌려주므로 `registry_error` 로는 못 잡는다 |
| 비용 | 응답에 내부 설정값(URI) 이 노출된다 |
| 다시 볼 조건 | 외부에 공개되는 API 가 되면 URI 를 가린다 |

### T10. MLflow stage(Production) 방식 유지

| 상황 | MLflow 3 에서 stage API 사용 시 폐기 예정 경고가 나온다 |
|---|---|
| 선택지 | (a) stage 유지 (b) alias(`@champion`) 로 전환 |
| 결정 | (a). 골격과 팀 문서 전체가 Production stage 기준이고, 기능 오류는 아니다 |
| 비용 | 경고 로그. 승격 시 이전 Production 을 Archived 로 내리지 않아 여러 버전이 Production 에 남는다 (`archive_existing_versions=True` 후속 과제) |
| 다시 볼 조건 | MLflow 가 stage API 를 실제로 제거할 때 |

### T11. 배치의 출발 여객은 있으면 실제값, 없으면 37,000

| 상황 | 골격은 보조 피처를 고정값으로 채운다. 실제 CSV 엔 출발 여객이 있다 |
|---|---|
| 선택지 | (a) 항상 37,000 고정 (b) 항상 실제값 (c) 선택 필드 |
| 결정 | (c). CSV 배치는 실제값, 랜덤워크와 `simulate_drift.py` 는 고정 |
| 비용 | 같은 배치라도 판정이 달라진다. 배치 10개 중 3개, 전체 21일 윈도우 995개 중 10.3% 에서 판정 변동. 기존 시연 수치(고정 조건) 와 직접 비교가 안 된다 |
| 다시 볼 조건 | 시연 수치를 하나의 조건으로 통일해야 할 때 |

80/20 분할 RMSE: 실제 출발 2,347 / 고정 2,682 / 전일값 2,734.

### T12. 스케일러는 Day1 에 한 번 fit 하고 재사용

| 상황 | fine-tuning 때마다 스케일러를 다시 fit 하면 모델 입력 분포가 바뀐다 |
|---|---|
| 결정 | `scaler.pkl` 을 Day1 에 한 번 만들고 Day1~3 내내 재사용. MLflow 모델 로드 시에도 고정 scaler 를 붙인다 |
| 비용 | 학습 범위(대략 35,000 ~ 40,000) 밖 수준으로 크게 이동하면 외삽이 안 된다 |
| 다시 볼 조건 | 수요 수준이 학습 범위를 오래 벗어날 때 |

### T13. 컨테이너 기본값은 eager 로딩

| 상황 | lazy 는 기동이 빠르지만 첫 사용자가 3.51초를 기다린다 |
|---|---|
| 결정 | 컨테이너는 eager (기동 2.15초, 첫 요청 0.096초) |
| 비용 | 모델을 못 읽으면 기동 자체가 실패한다. 실제로 MLflow 로더가 없던 시점에 `Application startup failed` 로 죽어 compose 에 `MODEL_SOURCE` 통로를 열었다 |
| 다시 볼 조건 | 기동 시간이 오토스케일링에 영향을 줄 때 |

### T14. 작업자 코드별 파일 소유

| 상황 | 5명이 하루에 같은 저장소를 동시에 고친다 |
|---|---|
| 결정 | A~E 코드마다 담당 파일을 정하고, 남의 파일은 고치지 않고 `code_current.md` 자기 섹션 "다른 영역에 요청" 에 적는다. `index.html` 만 D1 위쪽, D2 아래쪽으로 나눠 충돌 허용 |
| 비용 | 남의 파일의 한 줄 수정도 요청과 대기가 필요하다 (예: `reset_cache()` 부재로 승격 순간 500, A 의 PR 을 기다림) |
| 다시 볼 조건 | 인원이 줄거나 기간이 길어질 때 |

### T15. 요일, 공휴일 피처는 넣지 않는다

| 상황 | 주간 리듬이 있으니 달력 피처가 도움이 될 것 같았다 |
|---|---|
| 결정 | `exp/calendar-features` 에서 다음날 요일, 공휴일, 연휴를 넣어 봤지만 표본 밖 RMSE 2,344 → 2,695 로 나빠져 채택하지 않음 |
| 비용 | 구조 드리프트(요일 진폭 변화) 를 모델이 직접 볼 수단이 없다 |
| 다시 볼 조건 | 학습 기간이 늘어 연휴 표본이 충분해질 때 |
